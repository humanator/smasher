Canvas library options for workflow-editor

Comparing libraries that could power the DOT pipeline node/edge editor at the polish level of React Flow, without requiring React.

Evaluated against this project's actual shape: 6+ distinct node kinds (Codergen, Interviewer/gallery-gate, Tool, Manager, Conditional, SubPipeline) each needing a kind-specific attribute form, typed edges (condition/priority/loop_restart), and a save path that round-trips through a Rust/axum JSON API. Time estimates are rough engineering judgment for reaching a functional prototype (drag, connect, per-kind forms, save/load) in this codebase — not vendor claims. Each entry now also covers how the default look is customized — the mechanism (CSS variables vs. programmatic style APIs vs. bring-your-own-markup) and how far a redesign has to go before it stops looking like the library's own demo.

Same lineage as React Flow — built by the xyflow team or on their shared engine

Svelte Flow

MIT
Requires Svelte + Vite Maintainer: xyflow (same team as React Flow) Est: 3–5 days to functional

Not a clone chasing feature parity with React Flow — a sibling product from the same team, sharing the same underlying engine. Ships drag, zoom/pan, minimap, controls, background, and multi-select out of the box.

Customizing the look: restyle via CSS custom properties (e.g. --xy-node-background-color-default) scoped under .svelte-flow for quick token-level tweaks, or swap in fully custom Svelte components for node/edge types when a redesign needs to go further — both paths are first-class documented patterns, not workarounds. Built-in light/dark/system color modes out of the box.

Pros

  • Closest thing to "React Flow, no React" that exists — same authors, same design decisions, same polish.
  • Excellent docs, including a documented pattern for custom node types with arbitrary form content.
  • Small, fast-compiling framework — Svelte components compile away, minimal runtime overhead in a canvas-heavy UI.
  • Active, officially maintained, MIT licensed, no paywall for any feature used here.

Cons

  • Introduces a second frontend framework choice (Svelte) that's new to this codebase and this team.
  • Smaller ecosystem/hiring pool than React or Vue if this ever needs another contributor.
  • Needs its own build pipeline (Vite + svelte-preprocess) distinct from anything else in the repo.
Best fit: if adopting one new framework for this single surface is acceptable, this is the lowest-risk way to hit the "as polished as React Flow" bar exactly.

Porting to a Web Component: low–medium effort, and unusually clean compared to most frameworks — Svelte's compiler has first-party custom-element output (<svelte:options customElement="workflow-canvas" />, no third-party wrapper library needed). Write one thin wrapper component around <SvelteFlow>, compile it to a single <workflow-canvas> tag, and drop that tag straight into an otherwise-plain askama template — satisfying Assumption 1's "confined to the editor screens only" requirement more cleanly than mounting a separate SPA shell would. Two real snags, neither blocking: (1) complex data (the graph itself) has to cross the boundary as a JS property set imperatively from host-page JS, not an HTML attribute string — normal for any Web Component, not Svelte-specific; (2) Svelte 5's custom-element support is still maturing (there's an open enhancement issue on rough edges) — budget some slack for surprises. One genuine advantage: the compiler option shadow: "none" lets the element render in light DOM instead of a Shadow Root, sidestepping the usual "inject the library's CSS into the shadow root" headache entirely, since xyflow's CSS is already namespaced (.svelte-flow, --xy-* variables) and unlikely to collide with the rest of the page. Important framing: this changes how the editor is embedded, not whether Svelte is a dependency — you're still writing and building Svelte code, just distributing the output as one custom element instead of a mounted app.

Vue Flow

MIT
Requires Vue 3 + Vite Maintainer: community (bcakmakoglu), core now built on @xyflow/system Est: 3–5 days to functional

v2 was rebuilt on top of @xyflow/system — the same framework-agnostic core engine that now powers React Flow and Svelte Flow internally. Real engine parity, not a look-alike reimplementation.

Customizing the look: same CSS-custom-property theming system as Svelte Flow (inherited from the shared @xyflow/system core), plus fully custom Vue components for node/edge rendering when needed.

Pros

  • Genuine shared-engine parity with React Flow, inherited automatically as xyflow's core improves.
  • Vue's template syntax maps very naturally onto per-node-kind forms (v-if/v-for over your attrs map).
  • Large, mainstream framework — easier to find future contributors than Svelte.

Cons

  • Community-maintained, not an official xyflow product — roadmap and release cadence depend on one maintainer.
  • Still a new framework dependency for this codebase, same trade-off as Svelte Flow.
  • Docs are good but noticeably thinner than React Flow's/Svelte Flow's official docs.
Best fit: same case as Svelte Flow, but if Vue's larger ecosystem/mainstream familiarity matters more than having the framework's own creators behind the library.

@xyflow/system (raw engine)

MIT undocumented as public API
Requires nothing — you write the rendering layer Est: 3–4 weeks to functional

The shared low-level engine (drag/zoom/pan math, connection logic, viewport) that React Flow, Svelte Flow, and Vue Flow all sit on top of. In principle this is literally "React Flow's engine, no framework at all."

Customizing the look: no theming system ships with this package at all — the CSS variables and default component styles that make xyflow's other products easy to restyle live in the React/Svelte/Vue packages, not here. Every pixel is your own CSS/markup from day one.

Pros

  • The actual battle-tested interaction logic behind React Flow, with zero framework tax.
  • Total control over rendering — could integrate directly with a minimal DOM/HTMX-friendly layer.

Cons

  • Not published as a documented public API — a 2026 GitHub discussion shows users explicitly asking the xyflow team for an official framework-agnostic/Web Components release, unanswered as of this research. Building on it means depending on internals that could shift across versions with no migration guide.
  • You still have to build every bit of UI chrome (minimap, controls, node/edge rendering, selection UX) yourself — the "polish" that makes React Flow React Flow lives in the framework-specific packages, not this core.
  • Highest-effort, highest-risk option on this list for the least amount of ready-made polish.
Best fit: not recommended for v1. Worth revisiting only if xyflow ever ships an official vanilla/Web Components package.

General diagramming engines — framework-agnostic, very polished out of the box

AntV X6

MIT
Requires nothing — vanilla JS/TS core Maintainer: Ant Group, actively released (v3.1.7, updated within the last month) Est: 1–1.5 weeks to functional

A production-grade graph-editing engine used internally at Alibaba/Ant scale for DAG, ER, flowchart, and data-lineage diagrams. Ships built-in extensions React Flow itself needs plugins for: lasso selection, alignment/snap lines, minimap, undo/redo history, a stencil (node palette) panel — consolidated into the core @antv/x6 package as of v3.

Customizing the look: two tiers of control — quick reskins via each shape's markup/attrs config (SVG presentation attributes, similar to editing a template's style object), or a complete break from the defaults via HTML/React/Vue-rendered nodes (SVG foreignObject) for total bring-your-own-design control. No CSS-custom-property shortcut like xyflow's, but the ceiling is just as high.

Pros

  • Probably the single most feature-complete vanilla option — no framework decision needed at all.
  • Built-in snap lines, minimap, history (undo/redo), stencil panel, selection — less assembly than most alternatives.
  • Nodes can be plain HTML/DOM ("html-shape") — a per-node-kind form is just a DOM template, no framework required to build it.
  • Actively developed by a large team with production users; low abandonment risk.

Cons

  • General diagramming API (nodes/edges/ports as generic shapes), not dataflow-editor-specific — you define the node-kind/socket/attribute conventions yourself rather than inheriting them.
  • Docs are solid but translated-from-Chinese in places; some examples and community discussion are easier to find in Chinese-language sources.
  • v3's plugin consolidation is recent — some older blog posts/examples still reference the pre-v3 separate @antv/x6-plugin-* packages.
Best fit: the strongest choice if staying fully framework-agnostic (no Svelte/Vue/React anywhere) matters more than out-of-box dataflow-editor conventions.

Starting-point example — "Agent Flow": X6's own showcase ships an Agent Flow demo that maps unusually closely onto this project's shape. Pulled straight from its source (site/examples/showcase/practices/demo/agentFlow.ts in the antvis/X6 repo) it has: a left-hand Stencil palette with two collapsible groups — "Business Logic" (llm / code / branch / loop node types) and "Knowledge Base & Data" (kb / mcp / db node types) — dedicated Start/End flow cards, and draggable node "cards" rendered as real React components (@antv/x6-react-shape) with a themed header (icon, title, delete action) and either a description or an input field depending on kind, color-coded per node type. Ports stay hidden until you hover a node, turning blue once connected; edges get a hover-revealed delete button; node-kind definitions (icon/title/description/theme/ input) are loaded from a small JSON config rather than hardcoded. That's close to a direct template for this module's own node kinds — llm ≈ Codergen, branch ≈ Conditional, kb/mcp/db ≈ Tool, with Interviewer/ gallery-gate and Manager needing their own new card variants alongside it. Note it uses X6's @antv/x6-react-shape integration for the card rendering — real React function components, though only for node content, not the whole graph engine — so adopting this exact starting point still means a (small, scoped) React dependency for node rendering, unless those cards are rewritten as plain HTML nodes instead.

maxGraph

Apache-2.0
Requires nothing — vanilla TS Lineage: successor to mxGraph, the engine that powers draw.io Est: 2–3 weeks to functional

An extremely mature diagramming model (draw.io's own engine, rewritten in TypeScript), but it hands you the graph data structure and renderer, not ready-made UI chrome.

Customizing the look: a programmatic Stylesheet/CellStyle object model (properties instead of CSS strings, e.g. fill color/stroke/font as object keys) rather than CSS. Powerful and precise, but every visual decision is written in TypeScript, not CSS — no quick designer-friendly override path.

Pros

  • Proven at draw.io's scale and complexity — one of the most battle-tested diagram engines that exists.
  • No third-party runtime dependencies; fully vanilla TypeScript.
  • Extremely configurable/extensible for unusual diagram needs.

Cons

  • The project itself describes it as "under active development, still catching up to mxGraph's exact behavior" — younger and less stable than the code it replaces.
  • No built-in minimap/palette/inspector chrome — every bit of "React-Flow-grade" polish has to be built by hand on top of the model.
  • Steeper learning curve; mxGraph's API is famously dense.
Best fit: only if this editor is expected to grow into draw.io-level diagram complexity later — otherwise it's more engine than this module needs, for more effort than X6.

Purpose-built for node/dataflow editors — closest conceptual match to this pipeline's shape

Rete.js

MIT
Renderer: Lit (lightest), or Vue/React/Angular/Svelte Est: 1.5–2 weeks to functional

A TypeScript framework built specifically for visual-programming node editors — sockets, typed connections, controls, dataflow and control-flow execution engines. Conceptually this is the closest match to "nodes with per-kind attribute forms and typed connections," which is exactly what a Codergen/Interviewer/Tool/Manager DOT node is.

Customizing the look: since node/socket/connection components are ones you write yourself (Lit custom elements, or a Vue/React/Svelte/Angular component per the chosen renderer), there's no default theme to fight — full control from the first line of code, styled with ordinary CSS custom properties/Shadow DOM scoping. The trade-off: there's also no free "looks good already" starting point the way there is with xyflow or X6 — the visual design work is entirely yours.

Pros

  • Domain model (nodes, sockets, controls, connections) maps almost one-to-one onto this project's NodeType/attrs shape.
  • The Lit renderer is Web-Components-based — much lighter than adopting a full SPA framework, closer in spirit to staying framework-neutral.
  • Can mix renderers per node if ever useful (not needed here, but shows how decoupled the core is).
  • Has both dataflow and control-flow execution engines built in, if the editor ever needs live preview/simulation beyond static editing.

Cons

  • Less visual polish out of the box than xyflow/X6 — minimap, snap lines, selection marquee, etc. are not bundled; you assemble more of the "React Flow feel" yourself via the area-plugin/connection-plugin ecosystem.
  • Smaller community than xyflow or X6; fewer third-party examples to copy from for polish-level UI.
  • Plugin-composition API (core + area + connection + render + history, each a separate package) is more moving parts to wire up initially.
Best fit: if the editing/authoring experience (correct sockets, per-kind controls, connection validation) matters more than the canvas looking exactly like React Flow's default theme.

litegraph.js

MIT archived / folded into ComfyUI
Requires nothing — Canvas2D, zero runtime deps Est: 1.5–2 weeks to functional

The node-editor engine ComfyUI is built on — arguably the single best real-world proof that "AI-pipeline node graph with human-configurable nodes" can feel excellent to use at scale.

Customizing the look: two very different tiers again — a global JSON theme file (colors, node-slot colors, canvas background) is a quick, designer-friendly override, and ComfyUI itself ships a user.css layer for the surrounding DOM chrome. But because nodes are drawn on Canvas2D, redesigning what a node itself looks like internally (shapes, gradients, custom widgets) means writing custom draw functions, not CSS — noticeably more work than xyflow's or X6's "swap the component/template" model.

Pros

  • ComfyUI is the strongest existing proof point for exactly this project's use case (nodes = AI pipeline steps, humans configuring parameters, connecting a graph).
  • Canvas2D rendering handles hundreds of nodes smoothly; no DOM-per-node overhead.
  • Zero runtime dependencies, small footprint.

Cons

  • The standalone public repo (Comfy-Org/litegraph.js) is archived — as of August 2025 its development moved inside the ComfyUI frontend monorepo, with the import path changed to an internal path. Adopting it now means either an older frozen npm snapshot or forking, not an actively-versioned standalone library.
  • Rich per-node forms (the polish ComfyUI itself has) require building a custom widget system on Canvas2D, or overlaying real DOM forms positioned over canvas nodes — noticeably more manual work than xyflow's/X6's "just render a component/HTML template" model.
  • Real maintenance risk: no guarantee the frozen version keeps working as browsers/tooling evolve, since active development no longer targets it as a reusable package.
Best fit: compelling as a proof-of-concept reference to study (how does ComfyUI structure its node widgets?), risky as an actual dependency given the archival status.

Drawflow

MIT
Requires nothing — vanilla JS Est: 2–3 days to functional

Small, dependency-free flow-chart library — genuinely the fastest to a rough working prototype on this list, but visibly below React Flow's polish tier without significant custom CSS/UX work.

Customizing the look: straightforward — every node accepts arbitrary HTML content plus a custom CSS class, and there's a dedicated visual Theme Generator tool for producing a full reskin. Simple mental model, but the default aesthetic ceiling is lower than the other options, so "matching React Flow's polish" means doing noticeably more of that CSS work by hand.

Pros

  • Fastest initial setup of anything on this list; minimal API surface.
  • Zero dependencies, tiny bundle.

Cons

  • Default visuals and interactions are noticeably rougher than React Flow's — reaching the requested polish bar means a lot of custom CSS/JS on top.
  • Smaller contributor base; slower historical issue resolution than the other options here.
  • No built-in minimap, snap lines, or history — all DIY.
Best fit: a throwaway spike to validate the JSON API contract quickly, not the library to ship v1 on given the explicit polish requirement.

JointJS / JointJS+

MPL-2.0 core commercial +
Requires nothing — vanilla JS/TS, optional React/Vue/Angular bindings JointJS+: $2,990/license first year ($1,490/yr renewal), per developer Est: 1–1.5 wk on free core, 2–3 days on JointJS+

Splits cleanly into a capable free open-source diagramming core and a paid "+" tier that adds the inspectors, stencils, toolbars, and advanced layouts that actually get you to React-Flow-grade polish quickly.

Customizing the look: the free core's shapes are real SVG in the DOM, styleable with ordinary CSS (all SVG presentation attributes work as CSS properties) or per-subelement attrs config — genuinely easy, no proprietary styling language to learn. JointJS+ goes further and ships several complete built-in themes switchable at runtime via setTheme() — the fastest "looks professionally designed" path of anything evaluated, if the paid tier is on the table.

Pros

  • Mature, long-established library (predates most alternatives here) with a large diagram-type gallery.
  • JointJS+ ships a production-ready inspector/stencil/toolbar UI kit — if budget allows, this is probably the fastest path to a genuinely polished, form-driven node editor of anything on this list.
  • Free core is MPL-2.0 (real open source), not a crippled trial.

Cons

  • Reaching the requested polish level specifically routes through the paid tier — a real budget line (~$3k first year per developer) this codebase's other dependencies don't have.
  • Free core alone is general diagramming, not dataflow-editor-specific — similar assembly burden to X6, without X6's built-in minimap/snapline/history.
Best fit: worth a look only if a commercial license is acceptable — otherwise the free core doesn't clearly beat X6 for this project.

jsPlumb / Toolkit

MIT community commercial Toolkit
Requires nothing — vanilla JS, also ships a Web Component build Toolkit pricing: not publicly listed, per-developer + hosting tier, contact vendor Est: 1–1.5 wk community, 3–5 days Toolkit

Same free/commercial split as JointJS. The commercial "Toolkit" product is explicitly marketed as a React Flow alternative and ships as a genuine Web Component — meaning it can be dropped into any stack, including this one, with no framework at all.

Customizing the look: built around explicit client-side templating — you supply the HTML template for each node/group/port type and the Toolkit renders it, which is a natural fit for per-node-kind forms.   • Web Component packaging fits cleanly alongside an HTMX/askama app with zero build-tool entanglement.

  • Pricing isn't public — requires a sales conversation before knowing the real cost, unlike JointJS+'s published numbers.
  • Free community jsPlumb (connection-drawing only) is a much thinner base than the Toolkit; most of the "editor" experience is the paid product.
Best fit: the one commercial option genuinely worth a sales call if the team decides a paid product is on the table — its Web Component packaging is the best technical fit for this stack of anything on this list, free or paid.

Head-to-head: Svelte Flow vs. AntV X6

Both now have a concrete embedding story. Svelte Flow can compile to a single <workflow-canvas> custom element via Svelte's own compiler (no third-party wrapper) and mount into an askama template with one tag — see the Svelte Flow card above for the real mechanics and the two known snags. X6 needs no such step at all, since it was never React-only to begin with; its own React-shape node rendering (used in the Agent Flow example below) is an opt-in choice for node content, not a requirement of the engine.

If the Agent Flow example is genuinely a strong starting point (worth opening the link and judging the visual quality directly, not just this summary), X6 has a real time-to-first-good-prototype edge: cloning and re-theming an existing, working stencil+card+edge implementation is faster than building the equivalent from a blank Svelte Flow canvas, even with Svelte Flow's easier long-run re-theming story. That said, its node cards use @antv/x6-react-shape — so starting from it as-is brings a small React dependency in for node rendering specifically, which is worth weighing against the original "no React" preference even though the rest of the graph engine stays vanilla.

If long-run visual iteration matters more than initial velocity, Svelte Flow's CSS-custom-property theming and first-class custom-component escape hatch (from the earlier customization research) make it cheaper to keep reskinning over time; X6's per-node markup/attrs config gets more verbose as the number of distinct node kinds grows past the ~7 this project needs.

Bottom line

Free, staying framework-agnostic: AntV X6 is the strongest out-of-box match — it's the only option here that's both fully vanilla and ships minimap/snapline/history/selection built in, so the 1–1.5 week estimate goes almost entirely toward this project's own node-kind forms and save logic, not canvas plumbing. Its two-tier styling (quick attrs tweaks, or full HTML/React/Vue node override) also means "the default doesn't look good" has a real, documented escape hatch rather than a fight against the library.

Free, willing to adopt one small framework for this surface: Svelte Flow (or Vue Flow) is the lowest-risk way to get literally React-Flow-grade polish and the easiest re-theming of anything evaluated — CSS custom properties cover most restyling without touching a component, and swapping in fully custom node components is a first-class, documented pattern rather than a workaround.

Willing to spend money for speed and polish: jsPlumb Toolkit's Web Component packaging is the best technical fit for an HTMX/askama codebase of anything evaluated, and JointJS+ has transparent, published pricing (~$3k/developer year one) if that's preferred over a sales conversation — its switchable built-in theme packs are the fastest way to look professionally designed without doing the design work yourself.

Best conceptual fit for the actual editing model (typed node kinds, sockets, per-kind controls) if visual chrome can be assembled over a few extra days: Rete.js, especially via its lightweight Lit renderer — full styling control from day one, but budget real design time since there's no polished default to start from.

Worth flagging: maxGraph and litegraph.js are the two options where "if the default doesn't look good" turns into real extra work — both push node-internals restyling into code (a programmatic style-object API for maxGraph, custom Canvas2D draw functions for litegraph.js) rather than CSS, so budget more time for visual iteration if either is chosen.
